The cicada release loop scenario 3

The same repo and the same service, now shipping release candidates before it ships the release. prerelease-v1.5-rc cuts rcs that testers can install; main cuts the stable. Both compute from the same anchor, and only one of them writes a changelog.

repo acme/app package app arrangement prerelease line (#59) prerelease-v1.5-rc 1.5.0-rc.1 → rc.2 main 1.4.2 → 1.5.0
01

One line, two kinds of release

A feature and a fix land on prerelease-v1.5-rc, each answered by an ordinary release PR — the same loop as scenario 1, except the version carries an -rc.N suffix and no changelog is written. When the line is ready, prerelease-v1.5-rc merges into main and the stable release is cut from the accumulated history.

What Phase B does on an rc

Exactly what it does anywhere else. The versions file carries a prerelease field, so Phase B reconciles that tag — v1.5.0-rc.1 — against the same reachability and collision rules as a stable one, then creates the release object. On GitHub it is flagged prerelease: true; GitLab has no such field, so the adapter marks it in the release name instead. Same class of gap as draft PRs.

02

The anchor is the last stable, never the last release

This is the one rule the whole prerelease design exists to protect, and it is easiest to see by asking what the obvious alternative would have produced.

Which is why version does not move during an rc line

The field keeps its exact meaning from scenario 1 — last stable release — and that is what makes anchor resolution, range computation and the collision check apply to prereleases with no special case at all. The rc number lives in a second field that is deliberately not the anchor. Nothing in the anchor machinery learned a new rule.

03

What the counter does

Each run computes the target stable version from the commits as usual, then attaches -rc.N. Whether N increments or resets is decided by that base, never by a stored count.

04

cicada.toml

The whole file, so this scenario stands on its own — and it is byte-identical to scenario 1’s but for the one wider glob in release_branches. The prerelease line needs no stanza at all, because the built-in default already maps it.

What makes a branch a prerelease line

release_branches
Must list it, and has no default. A branch matching prerelease-* but absent here exits 0 quietly — the interlock that bounds what a defaulted classifier can do.
prerelease_branches
A glob list, same shape as maintenance_branches. Defaulted to prerelease/** and prerelease-*.
prerelease_identifier
One scalar, defaulted to rc. One line has one identifier, so there is no per-branch mapping and no precedence rule.
main
Matches no pattern, so it cuts stable. That is the entire difference between the two lines.
--prerelease rc
Ad-hoc on any branch, no config stanza needed; overrides the pattern where both apply.

Why it is branch-level, not per-package

the cost
Nothing new. It reuses the same pattern machinery as release_branches.
per-package
Would make an umbrella incoherent — aggregation has no meaning with some children on rc and others not.
here
One package, so the distinction is invisible — which is the point: the same rule scales to a monorepo unchanged.

It has to be a pattern, not a value on the branch

Putting prerelease = "rc" in prerelease-v1.5-rc’s own cicada.toml reads like it would work, and it does not: promoting the line merges prerelease-v1.5-rc into main, and that merge brings the config file along. main would start cutting rcs, and the only escape would be hand-resolving the config on every promotion — exactly the step that gets missed. With a pattern, both branches carry the same bytes, the merge is a no-op on the config, and main cuts 1.5.0 because it simply does not match prerelease-*.

05

.cicada-versions.toml

The prerelease line is the only thing that ever puts a second key in this file — and it is a key that is pointedly not the anchor.

before the line opens 
[packages.app]
version = "1.4.2"

Identical on main and on prerelease-v1.5-rc the moment it is cut. No prerelease key, because no rc line is open.

while the line is open · on prerelease-v1.5-rc 
[packages.app]
version    = "1.4.2"
prerelease = "1.5.0-rc.2"

version has not moved and must not — it is the anchor every computation here starts from. prerelease records only which rc is current.

after promotion · on main 
[packages.app]
version = "1.5.0"

The stable release rewrites version and deletes prerelease outright. The anchor moves exactly once per stable release, however many rcs preceded it.

Two fields, one of which is load-bearing

Everything that reads this file for an anchor reads version, and it means the same thing on every branch whether an rc line is open or not. Phase B is the only place prerelease changes behaviour: present, it reconciles the rc tag; absent, the stable one. That is the whole of the special-casing.

06

What a prerelease does not write

An rc is a real release — version files written, tag cut, forge release created, artifact buildable. It stops one file short.

The rc release PR, then, is the scenario 1 diff with one panel missing. Cargo.toml carries the prerelease version outright — that is what makes cargo build stamp the binary 1.5.0-rc.1, and what a tester ends up installing.

The two files disagree on purpose

During an rc line Cargo.toml reads 1.5.0-rc.1 while the versions file still reads version = "1.4.2". That looks like drift and is not: the versions file is the sole source of truth and Cargo.toml is an output, never read back to seed a computation. version is answering “where does the range start”, the manifest is answering “what does this build call itself”, and during a prerelease those are genuinely different questions. The field the manifest matches is prerelease.

The notes are still visible while the line is open

Skipping the file does not hide anything. Each rc’s release PR body and its forge release notes carry the full cumulative text since v1.4.2, which is exactly what a tester installing 1.5.0-rc.2 wants to read. cicada plan on prerelease-v1.5-rc says so too, reporting the rc version and that CHANGELOG.md will not be written — a silently skipped file write reads as a bug.

07

Promotion

There is no promote command. prerelease-v1.5-rc merges into main like any other branch, and main — matching no prerelease pattern — does what it always does.

Phase B first
The merged versions file still carries prerelease, so Phase B reconciles v1.5.0-rc.2 — already tagged, already released, a no-op.
anchor
version is still 1.4.2, so the range is v1.4.2..HEAD — the same range rc.2 used.
plan
1.4.2 → 1.5.0. The rc suffix is not carried over; it was never part of the base.
the diff
Cargo.toml 1.5.0-rc.2 → 1.5.0, one changelog entry, prerelease deleted.

cicada’s own rc commits ride along, and are inert

The merge brings R1 and R2 onto main with everything else, so they sit inside the v1.4.2..HEAD range that computes the stable release. They change nothing: chore(release): is a chore, whose section is bump = "none", hidden = true — it cannot justify a release and it cannot appear in an entry. The release PR title being conventional and non-releasable is what makes the promotion diff clean.

Decided — the line is the operator’s to retire

The prerelease key is deleted by the stable release, but that deletion is a commit on main. Until main is merged back into prerelease-v1.5-rc — or the branch is re-cut — prerelease-v1.5-rc still reads version = "1.4.2", prerelease = "1.5.0-rc.2". A new feat: there recomputes the same base 1.5.0, finds it unchanged, and cuts v1.5.0-rc.3 — an rc for a version that has already shipped, and one that sorts below it.

cicada does not detect this (#91). It acts on what the branch and the config say, and this branch says an rc line is open. Refusing would mean extending the collision check from the tag being created to the computed stable base — machinery added to notice a branch its operator stopped maintaining. The fix is a fast-forward: the line’s tip is already an ancestor of main, so merging main back conflicts on nothing, and afterwards the line reads 1.5.0 with no prerelease key and the counter resets.
