The cicada release loop scenario 4

The same repo and the same service, now shipping its Helm chart from the same tree. Two packages, two version lines, two tags — and no umbrella. One feat(app): moves both, and the way it moves the chart is the only dependency propagation cicada has.

repo acme/app packages app · app-chart shape app plus its chart (#14, #74) app 1.4.2 → 1.5.0 app-chart 0.9.0 → 0.9.1
01

One commit, two releases

A feature lands on main scoped to the app. Cicada answers with a single release PR carrying both packages, and when it merges, Phase B cuts two tags and creates two releases — because a changed chart artifact needs a chart version, even when nobody edited the chart.

Why the manifest is in both release bodies

This repo declares no umbrella, so there is no summary release to hang the manifest on. cicada embeds it in every release a run creates (#42), which means a reader of either release can answer “what else shipped with this?” without knowing which one is supposed to be the important one. Both copies are byte-identical — one artifact, not two renders.

02

Two lines, one declared link

The chart is its own package with its own version, its own tag format and its own changelog (#14). Exactly one thing crosses between them, and it is written in config rather than inferred from the filesystem.

This is the only dependency propagation in cicada

Everywhere else, blast radius is declared by the author through multi-scope commits — feat(auth,api): — and inferring it from Cargo or npm manifests is a permanent non-goal. Chart tracking is the single exception, and it earns it by being explicit: app_version = { track = "app" } is a line a human wrote, not a graph cicada walked. A changed chart artifact requires a new chart version, and cicada knows that only because you said so.

03

cicada.toml

The whole file, so this scenario stands on its own. It is scenario 1’s file plus one package stanza — and still no [umbrella].

cicada.tomlhuman-owned · committed
# acme/app — one Rust service and its chart, two version lines, no umbrella

[settings]
release_branches  = ["main"]                  # the gate: cicada acts only on these
default_scope     = "app"                     <- required unscoped commits are an APP change
committer         = "cicada[bot] <cicada@users.noreply.github.com>"
commit_source     = "commits"
release_pr_branch = "cicada/{branch}"
release_pr_title  = "chore(release): prepare release"

[forge]
kind = "github"                               <- required
repo = "acme/app"

[changelog]
sections = [
  { type = "feat",  title = "Features",      bump = "minor" },
  { type = "fix",   title = "Bug Fixes",     bump = "patch" },
  { type = "perf",  title = "Performance",   bump = "patch" },
  { type = "docs",  title = "Documentation", bump = "none"  },
  { type = "chore", title = "Chores",        bump = "none", hidden = true },
]

[packages.app]                                # package 1 of 2 — declared first, so released first (#96)
path       = "."
tag_format = "v{version}"
changelog  = "CHANGELOG.md"

[[packages.app.updaters]]
kind = "cargo"
path = "Cargo.toml"

# The chart is its OWN package with its OWN version line (#14).
# Not a child, not a sub-version — cicada draws no parent/child relation anywhere.
[packages.app-chart]
path            = "deploy/chart"
tag_format      = "chart-v{version}"          # a separate tag namespace — never collides with v{version}
changelog       = "deploy/chart/CHANGELOG.md"
initial_version = "0.1.0"                     <- required on helm (#88)

[[packages.app-chart.updaters]]
kind            = "helm"
path            = "deploy/chart/Chart.yaml"
app_version     = { track = "app" }           # appVersion mirrors the `app` package
on_tracked_bump = "patch"                     # the chart's OWN bump when `app` releases

# no [umbrella] — two packages is not a reason to invent an aggregate version (#73)

The four lines that make this shape 2

tag_format
Two namespaces, v{version} and chart-v{version}. Two packages sharing a tag shape is a check finding — it is a version collision waiting to happen.
app_version.track
The declared link. Names a real package or check fails.
on_tracked_bump
How big the chart’s own bump is when the app releases. Defaults to patch.
initial_version
Required on a helm package. Helm makes version mandatory in Chart.yaml, so the number already exists — cicada neither invents it nor reads it back (#75, #88).

Why no umbrella

nothing to aggregate
An umbrella aggregates a bump kind across children. With two packages one of which is derived from the other, the aggregate would restate what the app already said.
opt-in, always
cicada never assumes an aggregate version (#73). Declaring one is a statement that the set ships together under a single label.
default_scope
With no umbrella it must name a real package — here app, so fix: is an app fix.
04

Earned, derived, and both at once

The chart’s version can move for two unrelated reasons, and the interesting case is when both apply in one range.

An unscoped commit is a silent choice

fix: handle nil with default_scope = "app" is an app fix — so it bumps the app to 1.4.3 and drags the chart to 0.9.1. In scenario 1 the scope was decoration, because there was only one destination. Here it decides which of two packages moves, and the default decides it quietly. feat(app-chart): is the only way to say “chart only”.

Each changelog contains only its own package’s commits

The feat(app): add caching line appears in the root CHANGELOG.md and not in the chart’s — the chart did not receive that commit, it received a consequence of it. That is what makes the panel above incomplete rather than wrong.

A release with no commits explains itself

The chart received no commits, so its entry cannot be rendered from a range. The notes context carries derived_from instead — the package and version that caused the release — and the default template turns that into one line (#97).

Three things about that. The entry is written, not skipped: leaving it out would put a hole in the chart’s changelog where a real tagged release was, and a reader looking up 0.9.1 would find nothing. It is data, not prose cicada emits — core already labels the bump derived in the plan, so this only surfaces what exists, and the wording lives in a template you can override. And it is not an empty entry, which would be honest and would read as a rendering bug.

Rehearse it offline

cicada release-pr --no-push produces exactly this commit on a real local branch — no token, no network, no forge — and git show cicada/main displays all five files. The release manifest lands at target/cicada/release-manifest.json listing both packages, which under --no-push is the only place to inspect it, since no release object exists to embed it in.

06

The anchors diverge, and that is the point

Each package resolves its own anchor from its own recorded version, so each gets its own commit range. After one shared release the two anchors sit on the same commit; one chart-only change later, they do not.

Two failure modes worth knowing

A maintenance line refuses a dragged minor. With on_tracked_bump = "minor" on a branch matching maintenance_branches, an app release drags the chart above patch and the run hard-errors at exit 4. The message names the chart and its tracking relationship, not just the app commit — the cause is one step removed, and naming only the commit sends the reader to a file that looks correct.

An unquoted appVersion is a silent type change. appVersion: 1.10 parses as the float 1.1. Byte-splicing faithfully preserves whatever quoting it finds, so the helm updater always writes appVersion quoted and warns when it finds an unquoted value already there (#51).
