cicada · scenario walkthrough

The cicada release loop scenario 1

One repo, one Rust service, no umbrella. A feature goes out as a pull request, lands on main, and cicada answers with a release PR.

repo acme/app package app at rest 1.4.2 the change feat: add retry backoff outcome 1.5.0
01

The whole cycle

The loop closes on itself: cicada’s own commit at step 3 is what a human merges at step 4, and that merge is what triggers step 5. Step 3 is the part worth slowing down on — see below.

02

Base and head are different branches

The release PR merges into the branch it targets, like any other PR. What gets discarded and recomputed is the other end — the branch the PR is opened from, which cicada owns outright and rewrites on every push.

base  (target)
main — owned by humans. cicada only ever reaches it through a merge.
head  (source)
cicada/main — owned by cicada. Reset, rewritten, force-pushed.

Why discard instead of update

R2 is a pure function of three inputs: main’s tip, the anchor tag, and the config. Nothing in R1 is worth keeping — it is a stale answer to a question that has since changed. Rebasing R1 onto C would mean reconciling two changelog entries and two version numbers against each other, which generates conflicts for no gain.

The one exception: if the head’s tip is not cicada’s own commit, a human put something there that is not derivable from main. cicada refuses to clobber it — it drafts the PR, labels it cicada:stale, comments why, and exits 4.

One word, three meanings — so only one keeps it

“Release branch” was doing three jobs in the design docs: the git-flow line release/1.4, the allowlisted branch cicada runs on, and cicada’s own PR head. The first two are the same thing and keep the name. The third was renamed: the config key is now release_pr_branch, a sibling of release_pr_title, and in prose it is always the release PR branch — never shortened.

03

Inside step 3

What Phase B does at step 5

It finds 1.5.0 in the versions file, derives v1.5.0, sees it missing — and before creating it, replans from the previous tag. If the range now justifies more than 1.5.0, the release PR was merged while stale and cicada refuses. The comparison is one-sided: a recorded version higher than the recomputation is a deliberate over-bump and passes.

That check runs only when a tag is about to be created. Run on every push it would fire the moment the next fix: lands, because the range legitimately grows again. Tag and release object then reconcile independently, so a release call that fails after the tag lands is repaired on the next push rather than stranded.

Why B before A

If Phase A ran first it would still be anchored on the old tag, re-include everything the just-merged release contained, and propose releasing it all again — duplicate changelog entries, every cycle. cicada run does both in order so a CI file cannot express the broken one.

04

cicada.toml

Human-owned, read from the branch being released. This is the whole file for this repo — written by hand. There is no cicada init: scanning a repo to guess its layout is opinion that has to be reviewed line by line anyway, so check does the validation instead.

cicada.tomlhuman-owned · committed
# acme/app — one Rust service, no umbrella

[settings]
release_branches  = ["main"]                  # the gate: cicada acts only on these
default_scope     = "app"                     <- required unscoped commits land here
committer         = "cicada[bot] <cicada@users.noreply.github.com>"
commit_source     = "commits"                 # --no-merges; identical on squash/rebase repos

# the release PR cicada opens — its head branch and its title
release_pr_branch = "cicada/{branch}"         # the PR's HEAD; base is the branch above
release_pr_title  = "chore(release): {summary}"

# Branch *identity* is declared as patterns, never as a flag living on the branch.
# This repo has neither kind of line yet; both are shown for shape.
# maintenance_branches   = ["release/*"]      # patch-only: a computed minor is an error
# prerelease_branches    = ["prerelease-*"]  # cuts 1.5.0-rc.N instead of 1.5.0
# prerelease_identifier  = "rc"

[forge]
kind = "github"                              <- required never guessed at release time
repo = "acme/app"                            # optional — derived from origin when absent

# `bump` decides whether a type justifies a release at all.
# `title` / `hidden` only decide how it renders.
[changelog]
sections = [
  { type = "feat",  title = "Features",      bump = "minor" },
  { type = "fix",   title = "Bug Fixes",     bump = "patch" },
  { type = "perf",  title = "Performance",   bump = "patch" },
  { type = "docs",  title = "Documentation", bump = "none"  },
  { type = "chore", title = "Chores",        bump = "none", hidden = true },
]

[packages.app]                               <- required the package list is explicit, always
path       = "."
tag_format = "v{version}"
changelog  = "CHANGELOG.md"

[[packages.app.updaters]]
kind = "cargo"
path = "Cargo.toml"

# no [umbrella] — a single-service repo has no aggregate version to declare

What makes this the single-service shape

no [umbrella]
Opt-in. cicada never assumes an aggregate version.
one [packages.*]
Length 1 is not a mode — the monorepo path, with one entry.
default_scope
Points at the only package, so feat: and feat(app): are the same commit.
tag_format
Plain v{version}, because nothing needs disambiguating.

Things this config will not tolerate

tag_fromat = …
Unknown keys are an error naming the key, never a silent no-op.
feat(parser):
Unknown scope is fatal. check exits 3 with did you mean ‘app’?
chore(deps): …
Alone in a range it produces no release — bump is none.
no forge.kind
Required at release time; the error names the value it would have detected.

Still undecided in the design

{summary} in release_pr_title has no defined rendering yet — for one package or for many. The figures above assume chore(release): v1.5.0. It is one of the three items still open in docs/design.md.

05

.cicada-versions.toml

Tool-owned, written by cicada and committed by the release PR. It sits beside cicada.toml at the repo root, and it is the sole source of truth for versions — Cargo.toml is an output, never read back.

before any release 
// the file does not exist

An absent entry means never released. There is no sentinel version. The first release takes all reachable history and computes from 0.0.0.

at rest · steps 1–2 
[packages.app]
version = "1.4.2"

v1.4.2 is a real tag, reachable from HEAD. That tag — derived from this number — is the only anchor cicada has.

after step 4 
[packages.app]
version = "1.5.0"

Written by cicada on the release PR branch at step 3; reaches main only when a human merges. Step 5 derives v1.5.0 from it and tags.

A version and nothing else

No commit SHA. No date, no PR number, no changelog pointer, no label state. Every one of those was considered and removed: a stored SHA is a mechanism for silently continuing on a wrong range, and everything it was doing is now recomputed from the tag instead. The one field that can ever join it is prerelease, and only while an rc line is open on a branch.

The PR body is the same rendered notes the changelog entry carries — one template, two destinations, so they cannot drift. Cargo.lock is not in the list: cicada writes only what an updater declares.

Rehearse the whole thing offline

cicada release-pr --no-push produces exactly this commit on a real local branch — no token, no network, no forge. Inspect it with git show cicada/main. --dry-run stops one step earlier and prints the same diff without writing, because it is the identical computation with the write skipped.
