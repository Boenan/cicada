The cicada release loop scenario 2

The same repo and the same service, now shipping two lines at once. main is on 1.5.x; release/1.4 still owes its consumers patches. One fix, cherry-picked, releases twice under two different numbers.

repo acme/app package app arrangement trunk releases (#81) main 1.5.0 → 1.5.1 release/1.4 1.4.7 → 1.4.8
01

Two lines, one repo

A bug is found after 1.5.0 shipped. It is fixed on main and cherry-picked back onto the maintenance line. Cicada runs on both branches, from the same config, and neither knows the other exists.

Why the lines cannot collide here

This is the trunk-releases arrangement (#81): release/1.4 was cut only after main had already passed 1.4. So main computes 1.5.1 and the line computes 1.4.8 — different numbers, by construction. Cutting the branch too early, while main is still shipping 1.4.x, is the misconfiguration that makes both lines compute the same patch; the second one to run hits the collision check.

02

What made this need no setup

Cutting the line was two git commands and nothing else — no config edit, no flag written onto the branch, no state registered anywhere:

cutting the maintenance linethe entire setup
git checkout -b release/1.4 v1.4.7
git push -u origin release/1.4

That works because every piece of cicada’s state already lives inside the branch, and the one thing that could not — which kind of line this is — is a pattern rather than a value.

The failure a pattern avoids

A maintenance = true written onto each branch has to be remembered at every cut, and forgetting it means the guard silently does not apply. Worse, it travels: merging a release branch back into main — which the release-branch arrangement requires — would carry the flag along and quietly make the trunk patch-only.

03

cicada.toml

The whole file, so this scenario stands on its own. It is written once, on main, and every line cut from it inherits the same bytes — release/1.4 reads this exact file. Only the two highlighted lines differ from scenario 1.

cicada.tomlon main · and on every line cut from it
# acme/app — one Rust service, two live lines, no umbrella

[settings]
# which branches cicada acts on, and what kind of line each is
release_branches     = ["main", "release/*"]  # the gate (#26)
maintenance_branches = ["release/*"]          # patch-only lines (#28)

default_scope        = "app"                  <- required unscoped commits land here
committer            = "cicada[bot] <cicada@users.noreply.github.com>"
commit_source        = "commits"              # --no-merges; identical on squash/rebase repos

# the release PR cicada opens — its head branch and its title
release_pr_branch    = "cicada/{branch}"      # renders cicada/release/1.4
release_pr_title     = "chore(release): {summary}"

# no prerelease_branches — neither line cuts rcs

[forge]
kind = "github"                              <- required never guessed at release time
repo = "acme/app"                            # optional — derived from origin when absent

# `bump` decides whether a type justifies a release at all.
# `title` / `hidden` only decide how it renders.
[changelog]
sections = [
  { type = "feat",  title = "Features",      bump = "minor" },
  { type = "fix",   title = "Bug Fixes",     bump = "patch" },
  { type = "perf",  title = "Performance",   bump = "patch" },
  { type = "docs",  title = "Documentation", bump = "none"  },
  { type = "chore", title = "Chores",        bump = "none", hidden = true },
]

[packages.app]                               <- required the package list is explicit, always
path       = "."
tag_format = "v{version}"                    # v1.5.1 on main, v1.4.8 on the line — one format, two lines
changelog  = "CHANGELOG.md"

[[packages.app.updaters]]
kind = "cargo"
path = "Cargo.toml"

# no [umbrella] — a single-service repo has no aggregate version to declare

Read these as patterns, not settings

release_branches
Which branches cicada may release from. main and every release/*.
maintenance_branches
Which of those are patch-only. main does not match, so the guard never applies to it.
written once
On main. A branch cut from main inherits both, already correct.

The prefix is a namespace, not a label

{branch}
Interpolates release/1.4, slash and all — flattening it would map two lines onto one head branch.
renders
cicada/release/1.4 here, cicada/main on main.
why cicada/
It matches neither release/* nor main. A head of release/main would land inside the allowlist, so cicada’s own push would re-trigger it — on a branch that is patch-only besides.
04

When the wrong commit is picked

A maintenance line promises its consumers one thing: only patches. The interesting cases are all the ones where a cherry-pick brings something bigger — usually because the wrong commit was picked, or because the change belongs on a newer line.

It surfaces before the merge, too

cicada check --base release/1.4 --head <pr-head> reports the same problem at exit 3 while the pull request is still open — so the wrong cherry-pick is caught at review time rather than at release time.

05

What does not travel

Nothing changelog-shaped crosses between the two lines, in either direction. Going down — from main to the maintenance branch — that is not a rule cicada enforces. It falls out of which commit holds what.

Going up is the mirror image, and it is the one that surprises people: main’s CHANGELOG.md never mentions 1.4.8 either. That entry was written on release/1.4, in a commit that stays there.

This direction is accepted rather than fixed. Merging changelogs across release lines means reconciling independently-written files with no common ancestor for the new entries — a conflict generator. Each branch’s changelog describes that branch, which is arguably the correct reading anyway.

CHANGELOG.mdon main
## 1.5.1
### Bug Fixes
* reject empty auth header

## 1.5.0
…
CHANGELOG.mdon release/1.4
## 1.4.8
### Bug Fixes
* reject empty auth header

## 1.4.7
…

The same fix, two entries, two version numbers, two tags, two forge releases — and the two branches never reference each other. That independence is the entire point: it is what lets a maintenance line exist without any coordination mechanism at all.
